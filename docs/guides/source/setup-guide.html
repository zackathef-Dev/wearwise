Contents

Part 1

Before you start

What you'll build, what you need, and how to type commands.

1What you'll end up with

By the end of this guide, the whole WearWise system will be running on your own computer, with no accounts or services from the original developers:

1
A local backend

The database, logins and file storage, running inside Docker on your computer, filled with safe demo data.

2
The web dashboard

Running in your browser at localhost:5192. You'll sign in as a demo researcher.

3
The phone app

On an Android emulator (a virtual phone on your computer) or a real phone, talking to your local backend.

Time neededAbout 2–3 hours the first time, mostly waiting for downloads. Later, starting everything takes about 2 minutes.
Disk spaceAbout 25 GB free: Docker images (several GB), Android Studio and an emulator (about 15 GB), and the project (about 2 GB).
ComputermacOS, Windows 10/11 or Linux, with administrator rights, 16 GB of memory recommended, and an internet connection.

2How to use this guide (the terminal)

Most steps are commands you type into a terminal: a window where you type instructions instead of clicking. That's all a terminal is.

Your computerHow to open a terminal
macOSPress ⌘ Space, type Terminal and press Enter.
WindowsClick Start, type Terminal (or PowerShell) and press Enter.
LinuxPress Ctrl Alt T.

In this guide, commands look like this. Type the text after the $ (not the $ itself) and press Enter. Copying and pasting is fine.

Terminal: what you type, and what you should see
$ node --version
v24.19.0
  • Wait until the command finishes and the cursor comes back before typing the next one.
  • Some commands keep running (the dashboard and the app's bundler). Leave that window open, and open a new terminal window for the next command.
  • To stop a running command, click its window and press Ctrl C.
  • Text in angle brackets is something you replace, for example <repository-url>.
  • cd means "change directory" (go into a folder). Most commands must be run from the wearwise folder that you create in section 10.
Screenshots and output

The terminal output in this guide was captured on a real setup. Keys and private network addresses are hidden or replaced with examples, so your numbers will differ.

3What you need

  • A computer as described in section 1.
  • Access to the WearWise code repository, for example an invitation to the project's GitHub repository.
  • Google Chrome or Microsoft Edge. Patch setup needs one of them.
  • Optional: an Android phone with a USB cable, to use a real patch over Bluetooth.
  • Optional: the patch hardware: an ESP32 board and sensors (Part 5). Without a phone or patch, the emulator and the simulated patch drive the whole system.
Part 2

Install the tools

Six free programs, one at a time. After each one, a quick check proves it worked.

4Git (downloads the code)

  • macOS: in a terminal, run xcode-select --install and click Install, or download it from git-scm.com.
  • Windows: download the installer from git-scm.com and accept the default options.
  • Linux (Ubuntu/Debian): sudo apt install git.
Check
$ git --version
git version 2.54.0

5Node.js (runs the dashboard and builds the app)

Go to nodejs.org and download the LTS version (22 or newer). Run the installer with the default options. npm, Node's package installer, comes with it.

Check (open a new terminal first)
$ node --version
v24.19.0
$ npm --version
11.17.0

6Docker Desktop (runs the backend)

  1. Download Docker Desktop from docker.com and install it. On Windows, accept the offer to install or enable WSL 2, and restart if asked.
  2. Open Docker Desktop and accept its terms. Wait until it says Engine running (bottom left).
  3. Docker must be running whenever you use the local backend. You can set it to start when you sign in (Settings → General).
Check (open a new terminal first)
$ docker --version
Docker version 29.8.2, build 7fc2dff
"docker: command not found" on a Mac?

Close the terminal and open a new one. If it still happens, open Docker Desktop → Settings → Advanced and choose to install the command-line tools system-wide.

7Supabase CLI (controls the backend)

The Supabase CLI starts, stops and resets the local backend. Install it as a separate program:

SystemHow to install
macOSFirst install Homebrew (follow the one-line command on brew.sh), then run
brew install supabase/tap/supabase
WindowsFirst install Scoop (follow the commands on scoop.sh in PowerShell), then run
scoop bucket add supabase https://github.com/supabase/scoop-bucket.git
scoop install supabase
LinuxDownload the package for your system from github.com/supabase/cli/releases and install it (for example sudo dpkg -i supabase_*.deb).
Check: 2.120 or newer
$ supabase --version
2.120.0
Don't use "npx supabase"

The WearWise project blocks npm packages from running install scripts, for security, so the npm version of the Supabase CLI can't download its program. Always use the separately installed supabase command.

8Android Studio and Java (builds the phone app)

You need these to build and run the phone app, on an emulator or a real Android phone.

  1. Download Android Studio from developer.android.com/studio and install it. Open it and choose the Standard setup. It downloads the Android SDK and an emulator, which takes a while.
  2. In Android Studio: More Actions → SDK Manager. Under SDK Platforms, tick Android 16 (API 36). Under SDK Tools, make sure Android SDK Build-Tools, Platform-Tools and Emulator are ticked. Click Apply.
  3. More Actions → Virtual Device Manager → + (Create device). Pick a phone such as Pixel 8, then a system image with API 36 (click the download icon next to it), then Finish.
  4. Install Java JDK 17, the version WearWise was tested with. For example, use Eclipse Temurin 17 from adoptium.net (choose version 17 and the installer for your system).
  5. Tell your terminal where Android and Java are (below), then open a new terminal.

macOS: add these lines to the file ~/.zshrc

Run open -e ~/.zshrc (create the file with touch ~/.zshrc if it doesn't exist), paste the lines at the end, save, and open a new terminal.

~/.zshrc
export ANDROID_HOME="$HOME/Library/Android/sdk"
export PATH="$PATH:$ANDROID_HOME/platform-tools:$ANDROID_HOME/emulator"
export JAVA_HOME="$(/usr/libexec/java_home -v 17)"

Windows: set environment variables

Start → type environment variables → Edit the system environment variables → Environment Variables…. Under User variables:

  • New… ANDROID_HOME = C:\Users\<you>\AppData\Local\Android\Sdk
  • New… JAVA_HOME = the folder the JDK 17 installer created, for example C:\Program Files\Eclipse Adoptium\jdk-17…
  • Select Path → Edit → New and add %ANDROID_HOME%\platform-tools.

Linux: add export ANDROID_HOME=$HOME/Android/Sdk, the same PATH line as macOS, and JAVA_HOME pointing at your JDK 17 to ~/.bashrc.

Check (new terminal)
$ adb version
Android Debug Bridge version 1.0.41
Version 37.0.1-15733141
$ java -version
openjdk version "17.0.20.1" 2026-08-18 LTS

Building for iPhone needs a Mac with Xcode (from the App Store) and CocoaPods. See section 18.

About the "vulnerabilities" message

npm reports known advisories in the project's development tools (Expo CLI, Metro, Jest). This doesn't stop anything working, and the handover documents record it (docs/knowledge-transfer.md). Don't run npm audit fix --force: it downgrades Expo and breaks the app. Fixing them properly needs an Expo upgrade.

12Look inside the database (Studio)

Open http://127.0.0.1:54323 in your browser. This is Supabase Studio, a control panel for your local backend.

Creating a researcher account

Researcher and clinician accounts aren't created in the app. In Studio, open the SQL Editor, paste the file supabase/admin/create-viewer.sql, change the three values marked <-- CHANGE (email, role, name), and click Run. The result shows a one-time password: give it to the person privately. To turn an existing account into a researcher, use supabase/admin/set-role.sql the same way.

13Connect the apps to your backend

The dashboard and the app need to know the backend's address and its public key. One command finds both and writes them into each app's settings file:

Terminal (in the wearwise folder)
$ npm run backend:local

> backend:local
> node scripts/use-backend.mjs local

Mobile app (development builds) → http://192.168.1.20:54321
Dashboard (vite dev)            → http://127.0.0.1:54321

Restart Metro with a clean cache so the app picks it up:  cd apps/mobile && npx expo start -c
A phone must be on the same network as this computer, and the computer's firewall must allow port 54321.

Why two addresses? On a phone, "127.0.0.1" means the phone itself. So the app gets your computer's address on your Wi-Fi network (here 192.168.1.20; yours will differ), and the dashboard, which runs on the computer, uses 127.0.0.1.

Check what each app will use at any time:

Terminal
$ npm run backend:status

Mobile app, development builds: http://192.168.1.20:54321  (from apps/mobile/.env.development.local)
Mobile app, release builds:     https://<your-project>.supabase.co  (from apps/mobile/.env.production)
Dashboard, vite dev:            http://127.0.0.1:54321  (from apps/dashboard/.env.development.local)
Dashboard, production build:    https://<your-project>.supabase.co  (from apps/dashboard/.env)
If you use…Then
The Android emulatorThe default usually works. If the app can't reach the backend, run npm run backend:local -- --host 10.0.2.2 (the emulator's name for your computer).
A real phonePhone and computer on the same Wi-Fi (not a guest network). When your computer asks whether to allow incoming connections (macOS) or shows a Windows Defender Firewall prompt, click Allow (on Windows, for Private networks).
A different Wi-Fi network laterYour computer's address changes. Run npm run backend:local again and restart the app's bundler with -c (section 16).

These settings files (.env.development.local) are only used by development builds, so they can never leak into a release build. They're also excluded from Git. npm run backend:cloud switches back to the hosted backend (section 25).

Part 4

Run the phone app

Build the app onto an Android emulator or a real phone, then try the whole system.

16On the Android emulator

  1. In Android Studio, open Virtual Device Manager and click ▶ next to your virtual phone. Wait until its home screen appears.
  2. Open a new terminal window and build the app:
Terminal 3: leave it running
$ cd ~/Documents/wearwise/apps/mobile
$ npx expo run:android
… builds the app (5–15 minutes the first time), installs it on the emulator and opens it …
  1. WearWise opens on the sign-in screen, with no "backend not configured" message. Sign in as demo.participant@example.invalid / wearwise-demo-only. The demo recordings are restored into History.
  2. The terminal keeps running Metro, the "bundler" that sends the app its code. Leave it open while you use the app.

Next time

You only rebuild after changing native settings or updating packages. Normally, start the emulator, open the WearWise app on it, and start just Metro:

Terminal 3
$ npx expo start -c
Starting project at …/wearwise/apps/mobile
Starting Metro Bundler
warning: Bundler cache is empty, rebuilding (this may take a minute)
Waiting on http://localhost:8081
Logs for your project will appear below.
Android Bundled 3709ms node_modules/expo-router/entry.js (2346 modules)

-c clears Metro's cache. Always use it after backend:local or backend:cloud, because the backend address is built into the bundle. In the Metro window, press r to reload the app.

Expo Go won't work

WearWise uses its own native code (Bluetooth, encrypted storage), so it always runs as its own "development build" made by npx expo run:android. The Expo Go app from the Play Store can't open it.

17On a real Android phone

A real phone is needed to use a real patch, because emulators have no Bluetooth.

  1. Turn on Developer options: on the phone, open Settings → About phone (on Samsung: About phone → Software information) and tap Build number 7 times.
  2. Turn on USB debugging: Settings → Developer options → USB debugging on.
  3. Connect the phone with a USB cable. On the phone, tap Allow when it asks to allow USB debugging from this computer.
  4. Check the computer can see it:
Terminal
$ adb devices
List of devices attached
R3C…(your phone's serial)	device
emulator-5554	device
  1. Put the phone on the same Wi-Fi as the computer, then build and install:
    Terminal (apps/mobile)
    $ npx expo run:android --device
… choose your phone from the list …
  2. If the list says unauthorized, unlock the phone and accept the USB debugging prompt.
Phone not on the same Wi-Fi?

With the phone on USB you can route the backend through the cable: run adb reverse tcp:54321 tcp:54321, then npm run backend:local -- --host 127.0.0.1, then restart Metro with npx expo start -c.

Every development build follows this computer

Any phone that once ran a development build from this computer loads its code from Metro here (port 8081). Switching backend:local / backend:cloud and restarting Metro switches all of them.

You need a Mac with Xcode (App Store) and CocoaPods (brew install cocoapods). Then, in apps/mobile:

Terminal (apps/mobile)

A real iPhone also needs your Apple developer team chosen in Xcode. See docs/deployment.md (section iOS: macOS with Xcode). The iOS app has had less real-device testing than Android.

19Try the whole system

This walk-through uses every part: a new participant records with the simulated patch and shares with the demo researcher.

  1. Create a test participant: in the app, sign out if needed, tap Create Account, and use any address (for example you+test1@example.com), a password of 10+ characters, and tick the three boxes. You're signed straight in.
  2. Connect the simulated patch: Devices → Use Simulation. Home starts showing live readings. About 12 seconds later a practice possible fall alarm appears: tap I'm OK.
  3. Record: on Home, under Record, tap Start recording, wait a minute, then Stop recording → Stop. It appears in History and is backed up within a minute.
  4. Check the backend: in Studio, Table Editor → recorded_sessions now has your session.
  5. Share: Profile → Privacy & access → Share my data → Create code. Note the code.
  6. Add the participant on the dashboard: signed in as the demo researcher, click + Add participant and type the code. Your test participant appears. Open it to see the session.
Offline test (optional)

Turn on airplane mode, or run supabase stop, and record a session: it records normally and waits as "not backed up". Turn the network back on (or supabase start) and bring the app to the front: it uploads within a minute. Profile → Privacy & access shows the backup status and has Back up now.

The WearWise patch

Wire the sensors, install the firmware from the dashboard, and pair the patch with a phone.

Safety: ECG electrodes

Whenever ECG electrodes are on a person, power the board from a battery or USB power bank only, never from a mains-powered computer, charger or bench supply. The AD8232 module isn't isolated. WearWise is a research prototype, not a medical device.

21Install the firmware (Patch setup)

The easiest way needs no programming tools: the dashboard's Patch setup page installs the bundled firmware (0.9.6) over USB and gives the patch its Bluetooth PIN. It works in Chrome or Edge on a computer, signed in as a researcher or clinician. Nothing about the patch is sent to the backend.

  1. Plug the patch into the computer with a USB data cable (some cables only charge). Plug in one patch at a time.
  2. Click Connect patch and choose its port in Chrome's list: usually CP210x, USB Serial or USB-SERIAL CH340. No port listed? Install the USB driver for the board's chip (Silicon Labs CP210x or WCH CH340) and try again.
  3. The page shows the patch's Bluetooth name (WearWise-XXXX), its firmware version and whether it has a label PIN. Choose:
    Set upFor a new patch: installs the firmware, writes a new random PIN and erases the patch's settings (paired phones and Wi-Fi).
    UpdateNew firmware, keeps the PIN, paired phones and Wi-Fi.
    New PINFor a new participant: a new PIN and erased settings, firmware unchanged.
    Erase everythingPress and hold for 2 seconds. Wipes the whole patch. Set up can follow straight away.
  4. Print the PIN on a label and stick it on the patch. The participant types it when pairing.
"The patch didn't answer"?

Hold BOOT, tap EN/RST, release BOOT, and connect again. If it still fails, unplug the patch and plug it back in. Technical details under the card shows the full log.

Developers can also build and flash the firmware from source with ESP-IDF 5.4.2. See section 23.

22Pair the patch with a phone

  1. Power the patch (USB power bank or battery) and keep it near the phone.
  2. In the app: Devices → Pair a Device. Allow Nearby devices / Bluetooth if asked.
  3. Tap CONNECT next to the patch's name (on its label).
  4. Type the 6-digit label PIN when the phone asks. Ignore Android's "0000 or 1234" hint.
  5. Home starts showing the signals the patch has. Sensors it lacks say so.

Pairing rules (enforced by the patch)

  • A patch accepts a new phone only when it has never been paired, or within 60 s of pressing BOOT.
  • 3 failed attempts lock pairing until BOOT is pressed or a pairing succeeds.
  • It remembers two phones. A third replaces the oldest (press BOOT first). One phone is connected at a time.

Refused? In the phone's Bluetooth settings, remove the old WearWise entry, press BOOT, and pair again.

23Optional: build the firmware from source

Only needed to change the firmware. Install ESP-IDF v5.4.2 (Espressif's toolkit) as described in docs/firmware.md, then:

Terminal (ESP-IDF environment)
$ cd firmware/wearwise-esp32
$ idf.py set-target esp32
$ idf.py build
$ idf.py -p <PORT> flash monitor      # e.g. /dev/cu.usbserial-0001 or COM5; Ctrl ] quits the monitor

The serial log at start-up lists every sensor found. A board flashed this way that was never set up on the Patch setup page makes up its own PIN and prints it on this log.

25Moving to a hosted backend

The local backend is for development and testing. For a real study, the organisation runs WearWise on its own Supabase Cloud project, or on a self-hosted Supabase over HTTPS. The same code works with each, chosen only by configuration. In outline:

  1. Create a Supabase project under the organisation's account.
  2. supabase login, supabase link --project-ref <ref>, then supabase db push to apply the same migrations. Never load the demo data into it.
  3. Set Auth, email (SMTP) and Realtime settings in its dashboard.
  4. Put its URL and publishable key in apps/mobile/.env, apps/mobile/.env.production and apps/dashboard/.env, then run npm run backend:cloud and restart Metro.

Release builds accept only https:// addresses. The full steps, including release builds of the app and hosting the dashboard, are in docs/deployment.md.

Keep secrets out of the apps and the repository

The apps need only the project URL and its publishable key. Service keys, database passwords, access tokens and signing keys stay with their owner and are never committed. See docs/security.md.

The app can't reach http://192.168.x.x:54321Same Wi-Fi (not a guest network)? Firewall allows port 54321? Did the computer's address change? Run npm run backend:local again and restart Metro with -c. On the emulator, try --host 10.0.2.2.
Changed the backend but the app still uses the old oneThe address is bundled in: npx expo start -c, then reload.
"Invalid login credentials" with a demo accountThe database was reset without the demo data, or the app is on another backend: supabase db reset; npm run backend:status.
npx expo run:android fails to find the SDK or JavaCheck ANDROID_HOME and JAVA_HOME (JDK 17) from section 8, in a new terminal.
adb devices lists nothing, or unauthorizedTry another cable or USB port, turn USB debugging off and on, and accept the prompt on the phone.
Dashboard: "Not configured" pagenpm run backend:local, then restart npm run dev -w dashboard.
Can't see Participants or Patch setupYou're signed in as a participant. Use a researcher account (section 12).
Share code "invalid or expired"Codes work once, last 24 hours, and a newer code replaces an unused one. Make a new code.
Patch setup: no port in Chrome's listInstall the CP210x or CH340 driver, use a data cable, use Chrome or Edge.
Pairing refusedRemove the old WearWise entry in the phone's Bluetooth settings, press BOOT, pair again within 60 s with the label PIN.
A possible-fall alarm keeps appearing with the simulationOn purpose: about 12 s after connecting and after a recording starts or stops, then every 3 minutes. Tap I'm OK.
A phone you didn't mean to test with now uses the local backendIt's a development build following this computer's Metro. Run npm run backend:cloud and restart Metro with -c.

Many more cases are in docs/troubleshooting.md.

28Glossary

Repository (repo)The project's folder of code, with its history, stored in Git.
Terminal / command lineA window for typing commands (section 2).
Docker / containerSoftware that runs other programs (here, the Supabase backend) in self-contained boxes.
SupabaseThe backend platform WearWise uses: a Postgres database, logins, file storage and live messaging.
MigrationA file that creates or changes database tables and security rules. Applied in order.
Seed / demo dataMade-up accounts and simulated recordings, loaded into the local database only.
Row Level Security (RLS)Database rules that decide who can read or change each row. WearWise's privacy is enforced here.
Publishable key / secret keySupabase keys. The publishable key is safe inside apps. The secret key must stay private.
MetroThe bundler that sends the app its JavaScript code while you develop.
Development buildA test version of the app that loads its code from Metro on your computer.
EmulatorA virtual Android phone running on your computer. No Bluetooth.
LAN IP addressYour computer's address on your Wi-Fi network, such as 192.168.1.20.
PortA numbered "door" on a computer: 54321 (backend API), 54323 (Studio), 54324 (Mailpit), 5192 (dashboard), 8081 (Metro).
FirmwareThe program that runs on the patch's ESP32 board.
