2Security summary

Position statement

WearWise is a capstone research prototype that handles health-related data. Its security practices are informed by relevant guidance: the OWASP Mobile Application Security Verification Standard (MASVS), the OWASP Top 10, and Supabase's security recommendations. No part of the system has been certified, penetration-tested by a third party or formally audited, and it is not a medical device. Treat it as a prototype until the owner's own independent review says otherwise.

What is in place

  • Authorisation lives in the database. Row Level Security on every table, no privileges for anonymous users, least-privilege grants, and server-side checks for roles, account status, consent, 18+ and terms. 277 SQL checks and 8 pgTAP tests verify it.
  • Participant-controlled sharing. One-time hashed share codes create scoped, revocable grants. A participant's email is never shown to researchers.
  • Encrypted at every hop. Bluetooth LE Secure Connections with a 6-digit passkey. Optional Wi-Fi streaming over TLS with a certificate pinned over the authenticated Bluetooth link. HTTPS only in release builds.
  • Encrypted on the phone. SQLCipher database with its key in the OS secure store, Android backup off, screenshots blocked in release builds, and an iOS privacy cover.
  • No secrets in the code or the repository. The apps carry only the project URL and its publishable key. A handover scan found no credentials.
  • Hardened dashboard. Strict Content-Security-Policy allowing one backend host, no framing, HSTS, PKCE sign-in, and no caching of recordings.

Trust boundaries

  1. Radio (patch ↔ phone): Bluetooth LE, and optionally Wi-Fi on the local network. Anyone nearby can transmit, so links must be encrypted and authenticated.
  2. Phone ↔ Internet ↔ Supabase: HTTPS. The app and its publishable key are public, so every privilege decision is made by the database, never by the app.
  3. Browser ↔ Supabase: the same public API, with the same rules. The dashboard is a static site holding no secrets.
  4. Device storage: phones and patches can be lost or stolen. Data at rest on the phone is encrypted. On the patch it is not yet (R-01).
  5. Administration: Supabase project members, service keys and access tokens bypass Row Level Security, so they must be held by few people.

Design choices that reduce the attack surface: there are no Edge Functions and no server code of WearWise's own (Postgres functions and policies do the server work); the patch never talks to the backend; and the backend is chosen by configuration only.

Threat model

Who might attack WearWise, what they're after, and how each threat is handled.

5Assets and threat actors

Assets

Participants' health recordings and alerts · account credentials and sessions · the authorisation model (who may see whom) · patch pairing secrets · service keys and signing keys · availability of recording (it must not be lost).

Actors

A curious or malicious app user holding the public key · a researcher trying to see more than was shared · an attacker within radio range · an attacker on the same Wi-Fi · a thief of a phone or patch · automated abuse of sign-up · a compromised dependency · a careless or compromised administrator.

Part 3

Security controls

The controls in each layer, and where they live in the code.

7Patch firmware and Bluetooth

Pairing modeI/O capability DisplayOnly, bonding, MITM protection, LE Secure Connections only, 16-byte keys. A link that isn't Secure Connections, isn't authenticated or uses a short key is dropped and its bond deleted.
PasskeyThe 6-digit label PIN, written by the dashboard's Patch setup (random, guessable values like 123456 skipped, verified on the chip). A patch never set up there makes its own and prints it once on the serial console.
When pairing is allowedOnly with no bonds, or within 60 s of pressing BOOT. Three failed pairings lock pairing until BOOT is pressed (survives reboots).
BondsAt most two bonded phones or tablets. A third replaces the oldest. One connection at a time.
Link protectionEvery characteristic requires an encrypted, authenticated link. A link that doesn't authenticate is dropped after 30 s (60 s while the PIN prompt is up), so nobody can hold the only connection slot.
RandomnessSecrets are generated with the hardware true-random source enabled.
Serial consoleThe PIN is printed only for an unlabelled patch. Readings only in a debug build.
PacketsVersioned binary format with CRC-32. The app checks length, framing, version, sensor, encoding, CRC, session ID and patch ID on every packet.
At restOpen Flash, NVS (bonds, TLS key) and the PIN record are plain text, and ROM download mode is open (R-01). The documented fix is in the firmware README, "Production hardening": Secure Boot V2, flash encryption in release mode, NVS encryption and disabled ROM download. These burn eFuses (permanent) and need chip revision 3.0 or later plus a signed-update path in Patch setup.

Code: firmware/wearwise-esp32/main/communication/ (gatt.c, ble_pairing.c), main/core/factory_config.h. Protocol: docs/ble-protocol.md. The hardware tests of 14 October confirmed an encrypted, authenticated, bonded link with a 128-bit key on reconnect, and a fresh PIN pairing (H6, H13).

8Wi-Fi streaming

Bluetooth carries all data on its own. Wi-Fi is an optional, faster path on the same local network:

  1. The phone sends the network name and password over the authenticated Bluetooth link. The patch keeps them in RAM only. The phone keeps them in its secure store, per patch and per account.
  2. The phone reads the SHA-256 of the patch's self-signed P-256 certificate over Bluetooth, and opens wss://<patch-ip>/stream accepting only that certificate (native pinned-WebSocket modules).
  3. Within 3 s it sends a proof-of-possession value that only a phone which read it over authenticated Bluetooth knows. A wrong or late value closes the socket. Each socket is authenticated separately, with at most two sockets.
  4. Frames are byte-identical to Bluetooth packets and get the same checks. Release builds refuse Wi-Fi streaming without a pin.

Residual: the proof-of-possession value is 4 bytes, lasts one boot and is shared by bonded phones (R-10). The patch supports 2.4 GHz networks only. WPA2 passwords under 8 characters are refused before they're sent.

9Phone app

Local databaseop-sqlite with SQLCipher. The key is 32 random bytes in the OS secure store. If the store can't open, the app runs memory-only and says so: there is no plain-text fallback.
SessionStored by supabase-js in Keychain/Keystore with AFTER_FIRST_UNLOCK_THIS_DEVICE_ONLY. Sign-out wipes stored keys even offline. A fresh iOS install discards a session left by an earlier install.
Account isolation on one phoneThe device registry, saved Wi-Fi and sync state belong to the account. Notifications are cleared on sign-out. Sync checks account identity.
NetworkHTTPS only in release builds, checked at run time (public-config.ts) and at build time (scripts/check-release-config.cjs, which refuses http, loopback and private-LAN hosts, and any non-public key). The release Android manifest forbids cleartext traffic.
ScreensRelease Android builds set FLAG_SECURE (no screenshots or recent-apps previews). iOS shows a privacy cover in the app switcher.
BackupsAndroid allowBackup=false. Data is excluded from cloud backup and device transfer.
Deep linksEvery incoming wearwise:// link is validated before Expo Router reads it. Email links use PKCE.
Input from the patch and the cloudStrict protocol checks on Bluetooth and Wi-Fi. Restored recordings are checked (sample counts, sensors, rates) before display.
OtherShare code cleared from the clipboard after 2 minutes. Uploads sent as not cacheable. Generic error messages (no server details). Release Android permissions limited to Internet and Bluetooth (location only on Android ≤ 11, for scanning), plus vibration and notifications for alerts.
SigningThe owner's own release keystore (RSA-3072, created by create-release-signing.cjs). The build refuses to run without it.

10Accounts and authentication

  • Supabase Auth, email and password. Minimum 10 characters, enforced by the server. The apps also refuse common passwords and show strength (packages/password).
  • Sign-up gate. The create_profile_after_signup trigger refuses an account without consent, an 18+ confirmation and a terms version the server knows. The server stamps the times itself.
  • Roles are server-controlled: participant, researcher, clinician. Researcher and clinician accounts can't be self-registered. Administrators create them with supabase/admin/create-viewer.sql (one-time password, terms accepted by the person at first sign-in).
  • Account status: active or suspended. RESTRICTIVE policies stop suspended accounts uploading, and viewers see nothing. Suspension, role change and admin password reset end every session of the account.
  • Email links: PKCE in the app and the dashboard. Redirect allow-list: wearwise://auth/confirmed, wearwise://auth/reset and the dashboard's /reset-password.
  • Changing a password in the dashboard asks for the current one.

Not yet: multi-factor authentication (R-02), CAPTCHA or an enrolment code at sign-up (R-03), and leaked-password protection (a Supabase plan setting).

11Database access control

RLS is enabled on every table in public, and privileges start from nothing: anon has no table privilege and can execute no function. authenticated gets only what the apps use (pinned by a test), and RLS then decides which rows.

TableReadWrite
profilesOwn rowTrigger creates it. Own row, display_name column only, while active
recorded_sessionsOwn. A viewer: non-discarded sessions with a granted signalOwn, active and 18+ accounts. Server-stamped columns excluded
recorded_channelsOwn. A viewer: granted signalsOwn rows, into own sessions only
fall_eventsOwn. A viewer: if the grant includes fallsOwn, into own sessions
vital_alertsOwn. A viewer: granted signalsOwn. A session reference must be own and uploaded
access_grantsParticipant: own, including revoked. Grantee: live ones onlyRPC only
share_codes, share_code_attemptsNoneRPC only (no table privileges at all)

A "viewer" holds a live grant: not revoked, both accounts active, and the grantee still a researcher or clinician. Access ends the moment any of these stops being true. All RPCs are security definer with an empty search_path. A read-only schema fingerprint (supabase/admin/schema-fingerprint.sql) proves that a hosted database matches the migrations.

12Sharing and live view

  • Share codes: created by the participant with create_share_code(). Format XXXXX-XXXXX, about 49.5 bits from an unbiased generator, valid 24 h, single use. A new code replaces an unused one, and only the SHA-256 hash is stored.
  • Redemption (redeem_share_code()): researchers and clinicians only. 10 failures per hour per viewer, with a per-viewer lock against racing. Failures are returned as results, not errors.
  • Grants: scoped to signal types and whether falls are included. Either side can revoke (revoke_access_grant()), and the participant can narrow the scope (update_access_grant()). One live grant per pair. Revoked rows are kept as the participant's audit trail.
  • Privacy: list_shared_participants() returns display names only, never emails. Browser notifications on the dashboard say only what kind of alert.
  • Live view: started by the participant for 30 min to 8 h, on a private Realtime channel live:<grant id> that only the two parties may join. Nothing is stored. It pauses in the background, and removing or narrowing a viewer refreshes it at once. The phone acts only on stop, record and record-stop from a viewer, and a recording starts only when the participant taps Start.

13Storage and Realtime

  • Bucket recordings: private, 50 MiB per file, application/octet-stream only. Writes are allowed only into the uploader's own folder, by an active account, with exactly the name <uid>/<session uuid>/<channel uuid>.wwch. Reads: own folder, or a viewer with a live grant covering that channel.
  • Postgres changes: only fall_events and vital_alerts, INSERT and UPDATE only. DELETE events are not filtered by RLS, so they aren't published.
  • Broadcast: private channels only, no presence. alerts:<user id> may be joined only by its owner, and nobody may send on it.
  • Hosted setting: Realtime "Allow public access" off, so a client that forgets private: true fails closed.

15Repository, build and supply chain

  • No secrets in the repository. Real .env files, keystores, Apple signing files, device databases, build outputs and Supabase Studio's saved queries (supabase/snippets/) are gitignored. Templates are .env.example.
  • Install scripts disabled: the root .npmrc sets ignore-scripts=true, so dependencies can't run code at install time. The flasher library (esptool-js) is pinned.
  • Release checks: check-release-config.cjs (HTTPS public backend, publishable key, signing present) and tools/audit-apk.ps1, which checks a built APK for leaked secrets and developer paths.
  • Published history: the handover repository was published as a fresh history (14 October 2026). The personal data found in the original development history (a commit email, an old screenshot, absolute paths) is not in it.
  • Dependencies: see section 26 for current advisories. Never run npm audit fix --force: it downgrades Expo.

18Incident response

Follow the organisation's incident and privacy procedures. These playbooks cover the WearWise-specific steps.

IncidentImmediate steps
Service key, database password or access token exposedRotate it in the Supabase dashboard (Project Settings → API keys / Database), revoke exposed personal tokens, review Supabase logs for its use, run schema-fingerprint.sql to confirm the schema is unchanged, and remove the secret from wherever it leaked (history included).
Researcher or clinician account compromisedset-status.sql → suspended (ends sessions and hides every share at once). Then reset-password.sql, and review overview.sql for the affected participants. Reactivate once safe.
Participant's phone lost or stolenLocal data is encrypted and tied to the device's secure store. Run reset-password.sql for the account to end its sessions, and have the participant set a new password. If the phone was paired with a patch, use New PIN on that patch.
Patch lost or stolenTreat its bonds and TLS key as exposed (R-01). Participants Forget it in the app and remove it in the phone's Bluetooth settings. A recovered patch is reset with Set up (new PIN, settings erased).
Suspected unauthorised data accessSuspend the accounts involved, preserve Supabase logs, and involve the privacy officer. Notification duties (for example, Australia's Notifiable Data Breaches scheme) are the organisation's decision.
Vulnerable or malicious dependencyIdentify where it is used (npm ls <package>), update through npx expo install --fix or the Expo SDK, retest on devices, and rebuild and redistribute releases.

19Backups, logging and monitoring

  • Backups: enable the Supabase plan's backups or point-in-time recovery for the hosted database. Recordings also stay on participants' phones, and the cloud is an upload-only mirror plus a one-time restore onto a new phone.
  • Logs: Supabase keeps Auth, API and database logs for a period that depends on the plan. WearWise has no audit log of its own for researcher reads (R-08). Revoked grants are kept as the participant's audit trail.
  • No telemetry: the apps send no analytics or crash reports. The firmware prints no readings outside debug builds.
  • Monitoring to set up: storage growth (abuse, R-03), sign-up rate, failed sign-ins, and Realtime usage, using the Supabase dashboard's reports.

20Local development security

  • supabase start publishes the API, database, Studio and Mailpit ports on all network interfaces, so phones on the Wi-Fi can reach the API. Use it only on a trusted network, or firewall ports 54322–54324.
  • Development builds accept http:// to local and LAN hosts, and the Android debug manifest allows cleartext traffic. Release builds do neither.
  • Every development build on the network loads its code from the developer's Metro server (port 8081). Switching backends switches all of them.
  • Never use real participants' data on a local stack or a developer's machine. The demo seed refuses to run on a database that has accounts outside @example.invalid.
  • Test against hosted projects only with dedicated test accounts. rls-live.mjs creates random-password users and deletes exactly its own, but a separate development project is better.

25Owner responsibilities before real participants

  • Ethics and governance: an approved protocol, a data-storage region and retention period that match it, and a privacy notice. Fill in the organisation details in packages/legal/src/org.ts; the legal documents show a "draft" notice until you do.
  • Own deployment: a Supabase project under the organisation's account. Apply the migrations (never the demo seed), then confirm with the schema fingerprint.
  • Project settings: email confirmation on, own SMTP, Site URL and redirect URLs for the hosted dashboard only, Realtime public access off, minimum password length 10 (R-05).
  • Hosting: dashboard on HTTPS with the generated security headers (npm run deploy-config -w dashboard).
  • Keys: your own Android keystore and Apple signing, backed up. Database password and tokens in the organisation's secret store. Rotate anything ever exposed.
  • Accounts: one per person, created with the admin scripts, suspended when people leave. Few Supabase project members.
  • Patches: decide on production hardening (R-01) before patches go to participants. Label each patch and keep a register.
  • Backups: enable the plan's backups or point-in-time recovery.
  • Updates: keep the Expo SDK, React Native, Supabase CLI and images, and ESP-IDF current, and rerun every test suite after each upgrade.
  • Independent review before any use beyond a supervised research prototype.

BGlossary and references

RLS (Row Level Security)Postgres rules that decide which rows each user may read or change
RPCA database function the apps call by name. In WearWise, security definer with fixed checks
Publishable / anon keyThe public Supabase key that ships in the apps. Not a secret
Service-role / secret keyA Supabase key that bypasses RLS. Admin use only, never in an app
PKCEProof Key for Code Exchange: protects email sign-in and reset links from interception
LE Secure ConnectionsBluetooth Low Energy pairing based on elliptic-curve key exchange, here with a passkey
BondKeys a patch and a phone keep after pairing, so they reconnect encrypted
Certificate pinningAccepting only one known certificate (by its SHA-256) instead of any trusted one
PoPProof-of-possession: a value showing the phone read it over the authenticated link
SQLCipherEncrypted SQLite, used for the phone's database
CSPContent-Security-Policy: browser rules limiting where a page may load code and connect
eFuseOne-time programmable bits in the ESP32 that permanently enable security features
