2Summary

WearWise is a capstone research prototype for collecting wearable sensor data with the participant in control, developed as part of the La Trobe University CSE3CAP Capstone Project. The project owner, Shanmuga Sundar Dhanabalan, provided the original project brief and initial project context; the WearWise Project Team designed and implemented it, and made the implementation and prioritisation decisions during development. It has four parts:

  • an ESP32 sensor patch that measures heart rate, SpO₂, pulse wave, skin temperature, movement and ECG;
  • a phone app (Android and iOS) that pairs with the patch, records sessions into an encrypted database on the phone and backs them up;
  • a Supabase backend: accounts, the cloud copy of recordings, sharing, alerts and live view;
  • a web dashboard where researchers and clinicians see what participants chose to share, and which installs firmware on patches.
Status

WearWise works end to end and has been tested on real hardware, but it is a research prototype. It is not a medical device, its measurements are not clinically validated, and fall detection reports a possible fall only. Its security practices are informed by relevant guidance; nothing about it is certified or independently tested.

Ready

Code, firmware, database, tests and documentation, published as one tagged release with a clean history.

Verified

Two clean dry runs of the documented setup, all test suites, 13 hardware tests, and a hosted-schema comparison.

Owner's turn

Accounts and secrets of your own, governance, and a few decisions before real participants (section 6).

6The new owner's first steps

  1. Take over the code. Have the GitHub repository transferred to your organisation (or be added as an owner), clone it, and check out v1.0.0-handover.
  2. Run it locally. Follow the Setup Guide PDF or README.md: local Supabase, dashboard, app on an emulator. About two hours the first time.
  3. Set up your own backend. A Supabase project under your organisation's account, the migrations applied (never the demo seed), the project settings, and the first researcher account (section 16). Confirm it with the schema fingerprint.
  4. Decide on the original project. Have the team add you as Owner of the Supabase organisation that holds it, or retire it. Former members revoke their access and personal tokens.
  5. Create your secrets. Android release keystore, Apple signing, database password, SMTP credentials and access tokens, kept in your organisation's secret store. None are handed over (section 19).
  6. Build or source patches. An ESP32 board and the sensor modules in docs/hardware.md; install the firmware with Patch setup, which writes the PIN to print on each patch's label. Use New PIN whenever a patch changes hands.
  7. Governance before participants. Ethics approval, data region and retention, the organisation's details in packages/legal/src/org.ts (the legal documents show "draft" until then), and an independent security review.
  8. Make the open decisions below.

Decisions for the owner

DecisionWhy it matters
Lock patch hardware (Secure Boot, flash encryption)High A patch's flash is unencrypted: brief USB access can copy its pairing keys and PIN. The fix is permanent per chip and needs a signed-update process. Decide before patches go to participants.
Two-factor sign-in for staffMedium One leaked researcher password exposes every participant sharing with that person.
CAPTCHA or enrolment code at sign-upMedium Open sign-up lets scripted accounts fill storage.
Hosted project settingsMedium Email confirmation, SMTP, Site URL and redirects, Realtime public access off.
Retention policyMedium No automatic retention or purge exists; it must match the ethics approval.

The full risk register is in the Security Documentation, section 24; every limitation is listed in docs/known-limitations.md.

Part 2

How WearWise works

The system, the decisions behind it, and each component.

7System overview

A participant wears the patch. The phone app pairs with it over Bluetooth using the PIN on its label, shows live readings, and records sessions into an encrypted database on the phone. When online, it uploads finished sessions to Supabase. A participant can create a one-time share code; a researcher redeems it in the dashboard and can then read the shared signals, see alerts and falls, and, while the participant allows it, watch live view. Either side can end the sharing.

8Key design decisions

  1. Offline-first, the phone is the source of truth. Recording never depends on the network. The cloud is an upload-only mirror plus a restore path for a new phone.
  2. The patch has no backend knowledge. It speaks only to the phone, so the backend can move without touching firmware.
  3. One binary protocol with a shared fixture. Firmware and app test against the same packages/sensor-protocol/fixtures/v1.json.
  4. Capability discovery. The firmware reports the sensors it found; nothing assumes a sensor is there.
  5. Security in Postgres (Row Level Security), not in the apps. The publishable key is public by design.
  6. No custom server code. RPCs, triggers and policies replace an API server; no Edge Functions and no server secrets of our own.
  7. Configuration selects the environment (local, the owner's cloud, self-hosted). Release builds are HTTPS-only.

9Phone app

React Native 0.86 + Expo SDK 57, TypeScript, expo-router, zustand. Layers: app/ (screens), features/ (state per feature), domain/ (pure logic: recording engine, sync engine, fall detector, vitals), data/ (Bluetooth, Wi-Fi, SQLCipher store, Supabase) and platform/ (secure storage, notifications). It runs as a development build (npx expo run:android|ios), never Expo Go. A simulated patch exercises everything without hardware.

Local database: op-sqlite with SQLCipher, key in the OS secure store; inline migrations v1–v9 in src/data/local/sqlite-session-store.ts. Sample chunks are stored exactly as received, with CRC. Changing the schema means adding a migration step (never editing an old one) and a test.

Read: docs/mobile-app.md, docs/architecture/offline-first.md.

10Firmware and sensors

ESP-IDF 5.4 C project in firmware/wearwise-esp32/. SensorManager scans I²C and verifies chip IDs; drivers implement one interface (WearWiseSensor.h). gatt.c is the Bluetooth service, ble_pairing.c the PIN and pairing rules, ws_server.c the optional Wi-Fi stream. The version is in FirmwareConfig.h. Patches are flashed without a toolchain from the dashboard's Patch setup page, which also writes the label PIN.

SensorSignalsNotes
MAX30102Heart rate (1 Hz), SpO₂ (1 Hz), pulse wave (100 Hz)On-device heart-rate pipeline; SpO₂ uncalibrated
MAX30205Skin temperature (2 Hz)
MMA8452QMovement magnitude (50 Hz)The phone detects possible falls from it
AD8232ECG (250 Hz)Education only; battery power only with electrodes on a person

Read: docs/firmware.md, docs/hardware.md.

11Bluetooth protocol

One GATT service (57570000-5757-4b57-8000-574541525753) with INFO, CAPS, CONTROL, DATA, WIFI and TLS characteristics, all requiring an encrypted, PIN-authenticated link (LE Secure Connections). Data packets are a 58-byte header plus int16 samples plus a CRC-32, at most 462 bytes. Wire codes 1–6 never change meaning. Optional Wi-Fi streaming uses TLS with the patch's certificate pinned over the authenticated Bluetooth link.

Read: docs/ble-protocol.md.

12Backend, accounts and security

  • Supabase: Postgres 17 with Row Level Security, Auth (email and password), a private Storage bucket recordings, and Realtime (postgres changes for alerts and falls; private broadcast for live view). Nine tables, about 15 RPCs and a sign-up trigger, all created by supabase/migrations/. supabase/seed.sql adds synthetic demo data locally only.
  • Accounts: 10-character minimum password on the server. Sign-up must declare consent, 18+ and a known terms version, or the server refuses it. Email links return through wearwise://auth/* (PKCE). Researchers and clinicians are created by an administrator; nobody changes their own role.
  • Access rules: every table has RLS and least-privilege grants; anonymous users can do nothing; participants own their rows; viewers read only what a live grant covers; writes need an active, 18+-confirmed account. Verified by 277 SQL checks plus pgTAP and an API-level two-user test.

Read: docs/database.md, docs/security.md, and the Security Documentation PDF.

16Cloud deployment

  1. Create a project under the organisation's Supabase account (or use a self-hosted Supabase over HTTPS).
  2. supabase login, supabase link --project-ref <ref>, supabase db push. Never push the demo seed; never run supabase config push with the local configuration.
  3. Settings: email confirmation on, own SMTP, Site URL and redirect URLs for the hosted dashboard, Realtime "Allow public access" off.
  4. Create the first researcher with create-viewer.sql.
  5. Put the project URL and publishable key in apps/mobile/.env, .env.production and apps/dashboard/.env; npm run backend:cloud.
  6. Host the dashboard: npm run deploy-config -w dashboard (security headers for your backend), npm run build -w dashboard, and serve apps/dashboard/dist/ on HTTPS with single-page fallback.

Read: docs/deployment.md. The original capstone project's database differs from the migrations only by one comment; to keep it instead, see "Taking over the original capstone project" there.

17Release builds

AndroidJDK 17, Android SDK 36. .env.production with an https backend, your own keystore (node scripts/create-release-signing.cjs in apps/mobile, then back it up), npx expo prebuild --platform android, then NODE_ENV=production ./gradlew assembleRelease (or bundleRelease). The build refuses a non-HTTPS backend or a missing key. Check the APK with tools/audit-apk.ps1.
iOSmacOS, Xcode, CocoaPods. node scripts/check-release-config.cjs, npx expo prebuild --platform ios, open ios/WearWise.xcworkspace, choose your team (change the bundle identifier if taken), Archive.
FirmwareBump WW_FW_VERSION, build from a clean checkout (idf.py build), then npm run firmware:export -w dashboard; the manifest records the commit.

Part 4

Changing WearWise

Common changes, step by step, and how to keep the system healthy.

18Adding a sensor or a database field

A new sensor

  1. Firmware: a driver implementing WearWiseSensor.h, registered in SensorManager.c behind a WW_ENABLE_* flag.
  2. New kind of measurement only: the next free wire code (7 or 8) with scale and unit in both communication/protocol.{c,h} and packages/sensor-protocol/src/types.ts; regenerate fixtures (npm run fixtures -w @wearwise/sensor-protocol).
  3. App and dashboard: labels, units, ranges (apps/mobile/src/domain/vitals/), charts.
  4. Backend: widen the sensor-code checks in a new migration.
  5. Tests: firmware boot self-test, app tests, SQL suites, and a hardware-matrix row.

A new database field or table

  1. supabase migration new <name>. A new table needs RLS, explicit grants to authenticated, policies for each operation, and indexes on foreign keys.
  2. supabase db reset; add checks to a supabase/sql-tests/*.local.sql suite; run the suites.
  3. Update the app's sync gateway and types, and the dashboard's queries (apps/dashboard/src/data/).
  4. Document it in docs/database.md; on the hosted project, supabase db push. Never edit an applied migration: add a new one.

Secrets the owner creates and keeps

The Supabase project and database password, service keys, personal access tokens, SMTP credentials, the Android release keystore and Apple signing. None are in the repository, and none should ever be. The project URL and publishable key ship inside the apps and are public by design; Row Level Security protects the data.

Part 5

Limitations and next steps

What WearWise can't do yet, and where to take it.

20Known limitations

  • Team-defined implementation scope: Bluetooth LE was prioritised for the proof of concept, while NFC was deferred. The prototype supports one active wearable connection at a time. These are documented limitations and future-development opportunities rather than completed original requirements.
  • Measurements: research prototype, not clinically validated. SpO₂ is uncalibrated (a board read about 80 % at rest). Heart rate can read about double before settling, or on a weak module.
  • Falls: possible-fall detection is a threshold heuristic; nothing outside WearWise is alerted.
  • Testing coverage: emulators have no Bluetooth; iOS has had less real-device testing than Android, including the pinned Wi-Fi stream.
  • Patches: one phone connected at a time; a patch remembers two devices; the label PIN is fixed until changed with New PIN; firmware updates are USB-only; flash is unencrypted.
  • Accounts and data: no two-factor sign-in for staff; no in-app retention or purge; no audit log of researcher reads.
  • Paperwork: the legal documents are drafts until the organisation's details are filled in.
  • Dependencies: five advisories remain, all in build or test tooling or mitigated; they clear with an Expo SDK upgrade.
  • Cosmetic: Home's "Backed up x/y" counts a recording in progress as backed up until it stops.

21Future improvements

  • Calibrate SpO₂ against a reference pulse oximeter; validate heart rate against a reference (the AD8232 on the same board is a good start: docs/HRValidation.md).
  • Hold back heart rate until the estimate has settled.
  • Emergency-contact notification for falls, and interrupt-driven motion (MMA8452Q INT1 on GPIO27).
  • More sensors through the driver interface; an SPI sensor on the reserved pins.
  • Two-factor sign-in for staff; a column-limited view for viewers; read audit logging.
  • Retention controls and data export for participants.
  • Patch hardening (Secure Boot, flash encryption) with signed over-the-air firmware updates.
  • NFC connectivity and several patches streaming at once (deferred by the team for the proof of concept).
  • Extend the CI added at handover with an iOS build and on-device tests where a device farm is available.
  • An independent security review before any wider use.
