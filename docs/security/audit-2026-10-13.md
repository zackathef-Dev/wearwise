# WearWise security audit, 13 October 2026

> **Superseded in part by [WearWise-Security-Documentation.pdf](WearWise-Security-Documentation.pdf)**
> (14 October 2026), which has the current picture. Since this audit: firmware 0.9.6 remembers
> two phones instead of one owner, and drops an unauthenticated link after 30 s (60 s while the
> PIN prompt is up) instead of 15 s / 40 s; `.mcp.json` (R1) is not part of the handover
> repository; the repository has a private remote and was published as a fresh history (R5, R9);
> the database suites have 277 checks plus 8 pgTAP, not 261. This report is kept as the record
> of what was found and fixed on 13 October.

Scope: the phone app (`apps/mobile`), the web dashboard (`apps/dashboard`), the Supabase
database, storage and auth (`supabase/`), the patch firmware (`firmware/wearwise-esp32`)
and the repository itself (secrets, dependencies, hygiene). Five separate read-only
reviews, followed by fixes. The reviews and their attack probes ran against local
copies; the database fixes were then applied to production (see the database section).

This is an engineering review, not a penetration test, certification or medical-device
approval.

## Headline

- **No Critical findings.** No leaked secrets or service-role keys in the code, the
  history or the app bundle.
- **Two High findings, both in the firmware** (pairing and plain-text flash). The
  pairing one is fixed in code. The flash one needs a one-way hardware setting (secure
  boot and flash encryption), which is your decision; see "Decisions for you".
- Everything Medium or below that could be fixed in code has been fixed, except where it
  needs your decision or an account setting.

## Decisions for you

These need a choice, an account setting or money, so they weren't changed in code.

1. **Lock the patch hardware (firmware F2, High).** Turning on secure boot and flash
   encryption stops someone with brief USB access from copying a patch's keys or
   installing other firmware. It is **one-way**: a locked patch only accepts firmware
   signed with your key, the Patch setup page needs a signed-update flow, and an erase
   can leave a locked patch unflashable over USB. It needs ESP32 chip revision 3.0 or
   later. The steps are in the firmware README under "Production hardening". Suggested:
   do it before patches go to participants, not on development boards.
2. **Two-factor sign-in for researchers and clinicians (database B1, Medium).** One leaked
   staff password exposes every participant who shares with that person. Supabase
   supports authenticator-app codes; the dashboard would need an enrol and verify
   screen, and the database can then require it for staff. Also turn on "leaked password
   protection" in Supabase Auth if your plan includes it.
3. **Stop automated sign-ups (B4, Medium).** Anyone with the public app key can create
   accounts and upload until the project's storage fills. Options: a CAPTCHA on sign-up
   (Cloudflare Turnstile or hCaptcha, free tiers) or a study enrolment code that
   participants get from the team.
4. **Email and links (B12, Low).** Once the dashboard has a hosting address: set
   Supabase's Site URL to it, allow only its `/reset-password` page, remove the
   `localhost` entries from production, and set up your own email sender (SMTP).
   The built-in one sends only about 2 emails an hour.
5. **Development-tool access to production (R1, Medium).** `.mcp.json` gives a development tool's Supabase
   connection write access to the production database. Make it read-only and limited to this
   project (`--read-only --project-ref=<project-ref>`), or remove it and use a
   development project.
6. **Proving a patch is genuine (M2, Medium).** The full fix is a per-patch secret
   printed on the label (next to the PIN) that the app checks with a challenge on every
   connect, before sending the Wi-Fi password. It's a firmware, Patch setup and app
   feature, about a day or two of work.
7. **Account deletion in the app (B3).** Deletion now works end to end for the study
   team (`node supabase/scripts/admin.mjs delete-account <email>` removes the recordings
   and then the account). A "Delete my account" button in the app is a separate feature.

**New process rule:** whenever the terms change (`ACCEPTANCE_VERSION` in
`packages/legal`), a migration must add the new version to `private.terms_versions`
before an app that sends it ships. Otherwise sign-up and "Before you continue" fail.

## Web dashboard

| # | Severity | Finding | Status |
|---|---|---|---|

## Database, storage and sign-in (migration 9)

Fixed in `supabase/migrations/20261016000009_security_review.sql`, with small changes to
migrations 7 and 8. The local test suite went from 160 to 261 checks.

**Live since 13 October 2026.** Migrations 6–9 were applied to the production project
in order, each checked against its SHA-256 first, with no errors. Post-checks:
- The only terms version is `2026-10-16`.
- The `recordings` bucket is private.
- The Realtime publication sends inserts and updates only.
- `anon` holds no table or function privileges; an anonymous request to any table or
  RPC now gets "permission denied".
- A two-account isolation test passes 19/19.
- Realtime is private-only ("Allow public access" off).

| # | Severity | Finding | Status |
|---|---|---|---|

| B2 | Medium | Every researcher or clinician a participant shared with could see the participant's email | **Fixed.** No longer returned; the dashboard shows the display name or a short participant code. The privacy policy and the share screen say so |

## Patch firmware (now 0.9.3)

| # | Severity | Finding | Status |
|---|---|---|---|
| F1 | High | The first-use pairing window plus a fixed label PIN let someone nearby guess their way to a lasting bond | **Fixed.** 3 failed pairings lock pairing until BOOT is pressed (survives reboots); a new pairing removes every other phone's bond (one owner); Secure Connections only |
| F2 | High | Flash is unencrypted and ROM download is open: brief USB access gives bonds, the TLS key and the PIN, enough to clone the patch | **Your decision** (secure boot and flash encryption; one-way, see above). Steps are in the firmware README, "Production hardening" |
| F3 | Medium | Any Bluetooth device could hold the only connection slot forever | **Fixed.** Unsecured links are dropped after 15 s (40 s once the PIN prompt shows) |
| F4 | Medium | Wi-Fi stream authentication was global: another device on the network could cut the stream or race for packets | **Fixed.** Per-socket authentication with a 3 s deadline; constant-time PoP check |
| F5 | Medium | Secrets were generated before the radio was on, when the chip's random generator is only pseudo-random | **Fixed.** Generated with the bootloader's true-random source enabled |
| F6 | Low | "Just Works" pairing could evict a real phone's bond | **Fixed.** Refused unless pairing is open and the bond is authenticated |
| F7 | Low | Legacy pairing and short keys were accepted | **Fixed.** Secure Connections only, 16-byte keys |
| F8 | Low | The PIN and heart-rate values were printed on the serial console | **Fixed.** The PIN only for an unlabelled patch; readings only in a debug build |
| F9 | Low | The Wi-Fi PoP is 4 bytes, lasts the whole boot and is shared by bonded phones | **Partly.** Constant-time check and the 3 s deadline (F4). The size is part of the protocol and is unchanged |
| F10 | Low | Unsynchronised WebSocket sends; the server could be freed mid-send | **Fixed.** All sends are queued on the server's own task |
| — | — | A Wi-Fi password the driver refused rebooted the patch | **Fixed.** The setting is refused with an error and the current network stays up; the app says so |

Needs testing on a real patch with phones: first pairing on iOS and Android, the
lock-out, moving the patch to a new phone, the 15 s timeout with a slow Android pairing
prompt, a long Wi-Fi stream, and a too-short Wi-Fi password. The list is in the firmware
README.
